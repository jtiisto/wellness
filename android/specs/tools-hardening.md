# Spec: Tools Parity + Hardening (Phase 8)

Status: **approved 2026-08-09** (v2.1 after two Codex passes — 34 findings folded; user-approved with close-and-reopen switching, opaque-ids-kept dump policy, and flush-Worker-in/periodic-deferred)

> **v2.1 (switch-flow Codex fold):** (1) **Quiescence contract** — `SyncScheduler.stop()` cancels timers only; an in-flight sync completing after the wipe would `applyDelta()` old-server rows AND the old watermark back into Room, silently defeating the full-pull promise. The switch now: closes a process-wide `ServerSessionGate` (every network-to-Room writer — both sync stores' apply paths, `TrendsRepository`/`AnalysisRepository` cache writes — checks it before writing), stops schedulers, **drains both sync mutexes by locking them**, runs `AnalysisStore.stopAndJoin()` (lifecycle callbacks disabled, new ops rejected, control-scope children cancelled and joined), cancels WorkManager work and **awaits the `Operation`** (noting `getInstance()` can throw pre-init — guarded), and only then wipes. Pinned by delayed-response tests asserting no post-wipe rows or watermarks. (2) **Restart replaced by close-and-reopen** — `NEW_TASK|CLEAR_TASK` + `exit(0)` restarts a *task*, not a process, with no relaunch guarantee; the dialog now says the app will close and asks the user to reopen it; on confirm: wipe commits → `finishAffinity()` + `exit(0)`. Deterministic, no trampoline process (rejected alternative recorded). (3) **Fail-closed boot resolution** — `no active row` (→ Built-in) is distinguished from `read failure` or `multiple active rows` (→ a recovery screen with retry; NO HTTP client, NO schedulers — falling back to BuildConfig with another server's data in Room would upload B's records to A). Suspend DAO under a bounded `runBlocking(Dispatchers.IO)`; never `allowMainThreadQueries()`. (4) Active-flag updates are one atomic `UPDATE … SET isActive = CASE WHEN id=:target THEN 1 ELSE 0 END`; the boot query rejects >1 active. (5) Deleting the ACTIVE profile is a single transaction (wipe + delete row + clear flags) behind one dialog disclosing BOTH the deletion and the full data loss. (6) The switch wipe also deletes `cache/shared/` export/dump files (an old-server export must not outlive the switch; copies already in recipient apps are gone regardless). (7) A **synchronous** boundary line (`server switch: <old-nickname> → <new-nickname>`) is written to `debug_log` inside the switch transaction — `DebugLog.log()` is fire-and-forget and would race the exit; dumps disclose that entries may span both servers within the 1 h window.

> **v2 (Codex fold):** (1) `forceSync()` is a dedicated store entry point — `triggerSync()` always reads the stored watermark and cannot do a full pull. (2) Coach full pulls get **full-snapshot semantics** — the server sends `deletedPlanDates` only for incremental pulls, so a forced pull must transactionally delete window-local plans absent from the response or server-deleted plans survive "full reconciliation" forever. (3) Post-force-sync scheduler ownership defined (`resetRetry()` on success, `requestSync()` when still dirty). (4) Isolation blocks rethrow `CancellationException`. (5) Watermark regression declared accepted-and-safe (replay-only). (6) Export mapping is a column-by-column table incl. dirty state under PWA keys and `_deleted` injection; `app_schema_version` **omitted** (it describes the PWA's IndexedDB schema; substituting Room's would lie). (7) `app: {activeModule: null}`; `server_profiles` **excluded from the export** (tailnet URLs are config, not data — privacy deviation). (8) Export reads one `withTransaction` snapshot, then streams. (9) Streaming operationally defined: bounded model in the transaction, `encodeToStream` (pretty 2-space, PWA parity) to the cache file — object and encoded string never coexist. > **v2.2 (code-review fix round, 2026-08-10):** Codex on the working tree — 2 BLOCKERs + 3 MAJORs + 1 MINOR. (1) **The only path that changes the active server is the switch flow**: URL edits on the ACTIVE profile are prohibited (nickname edits remain allowed) with copy `"To change the active server's address, add it as a new profile and switch to it."` — a direct `rename` on the active row was a full bypass of quiescence + wipe. (2) **`ServerSessionGate` becomes a writer LEASE**: every server-scoped Room write — journal/coach LOCAL MUTATORS included (the original gate missed them entirely), sync apply paths, trends/analysis cache writes, the flush Worker — runs inside `withWriteLease { }`; `close()` rejects new leases AND awaits outstanding ones before the wipe proceeds. This closes both the unquiesced-local-mutation blocker (a coach edit suspended at `clientId()` landing post-wipe) and the trends check-then-write race (a write admitted before `close()` completing after it) with one mechanism. Mutex drains remain on top. (3) **Flush Worker returns `Result.retry()` on OFFLINE skips** — WorkManager's CONNECTED constraint passes on captive/unvalidated Wi-Fi where the app's validated-internet check reports offline; returning success there abandoned the only durable retry. `ALREADY_SYNCING` stays success (an active sync owns the work). (4) **Safety tests use real barriers**: controllable DAO fakes blocked mid-write across the close, all-8-table emptiness asserted after releasing blocked writers, active-URL-edit prohibition covered, trends post-lease race pinned, worker retry matrix added; the instrumented switch-transaction test seeds all 8 wiped tables. (5) GitStamp reports `-dirty` only when `git status` itself succeeded; command failure yields the literal `unknown` with no dirty suffix. ## Declared decisions & deviations

1. **Force sync** — new `forceSync(): ForceSyncModuleResult` on `JournalSyncStore` and `CoachSyncStore` (NOT via `triggerSync()`, which reads the stored watermark; NOT an extension of scheduler-facing `SyncResult`): `tryLock()` once (busy → `Skipped(BUSY)`), offline preflight per module (`Skipped(OFFLINE)`), run a force cycle — upload dirty first (coach contract), then **null-watermark full pull**, apply, stamp the returned `serverTime`. Orchestrator runs coach then journal, each isolated; isolation blocks **rethrow `CancellationException`** and convert only real failures. After each module: on success `scheduler.resetRetry()`; if dirty rows remain and online, `scheduler.requestSync()` (the PWA's finally-re-request — a mid-force-sync edit must not wait for the next poll). **Watermark regression is accepted and safe**: the server stamps wall-clock-minus-2s; a lower stamp only replays deliveries, and application is idempotent by protocol.
2. **Coach full-snapshot rule** (parity-critical): on a null-watermark pull the server omits `deletedPlanDates`, so the force path transactionally deletes local `coach_plans` rows inside the window that are absent from the response **before** upserting — otherwise a server-deleted plan survives forever. Logs merge skipping dirty dates exactly as the normal path. Pinned by a stale-local-plan test. (Journal needs no equivalent: a full delta includes all deleted tracker ids — verified.)

   *(v2.2)* The snapshot is trusted for the deletion but **not for the watermark**. "Every local plan removed by a response that carried none of its own" is a legitimate empty schedule and also exactly what a server answering from an empty or half-restored database looks like; nothing in a 200 distinguishes them. So in that one case the deletion still applies (the rule is right, and it cannot be re-derived later) while `applyDownload` **skips the watermark write in the same transaction**, leaving one ordinary incremental pull able to restore whatever the server really has. An empty snapshot that had nothing to wipe advances the watermark as usual — the guard is about the wipe, not about emptiness.
3. **Force-sync result copy** — full matrix. Per module: `success(counts)` / `failed` / `skipped(offline)` / `skipped(busy)`. Lines: journal success `"Journal: N records accepted, M conflicts"`; coach success `"Coach: N days uploaded"`; failed `"<Module>: failed"`; offline-skip `"<Module>: offline"`; busy-skip `"<Module>: sync already running"`. Dialog styling: success iff ≥1 module succeeded; both skipped → `"No modules synced."`; offline is evaluated **per module at its start** (a network drop between coach and journal yields coach success + journal offline — reachable and rendered honestly). Confirm copy: `"This will reconcile all data with the server. Continue?"`; busy button `"Syncing…"`. Journal's PWA `uploaded` ≡ `accepted` duplicate is dropped.
4. **Export** — one **`withTransaction` snapshot** into a bounded model, then `encodeToStream` (pretty 2-space, PWA parity) to the cache file; the model and the encoded string never coexist in memory. v2 envelope, column-by-column:

12. **Server address book with wipe-and-resync switching** (user semantics: "server change should wipe all local data, and do a full sync from the server"):
    - **Model**: Room v5, `server_profiles(id INTEGER PK AUTOINCREMENT NOT NULL, nickname TEXT NOT NULL, url TEXT NOT NULL, isActive INTEGER NOT NULL DEFAULT 0)`; at most one active row; no active row = BuildConfig default, rendered as the first, undeletable "Built-in" entry. Ascending-id display order. Duplicates allowed. Migration 4→5 + 1→5 chain tests (run next emulator session); plan §4 amended at approval.
    - **Validation**: trim both fields; nickname nonblank ≤40 chars; URL absolute `http(s)`, nonblank host, optional port/path, NO user-info/query/fragment, trailing slash normalized before store, ≤200 chars. Stored plaintext in Room — tailnet URLs, non-sensitive, noted.
    - **CRUD UI**: add/edit via dense fields (Round 4: the `NAKED` skin, which draws no label, no supporting text and no error box — the dialog states each of them itself, the error on the field's *own* semantics node so a screen reader hears it from the field it belongs to); delete via M3 AlertDialog — title `"Delete server?"`, body `"Remove \"<nickname>\" from the list?"` (destructive button "Delete", dismiss "Cancel"); deleting the ACTIVE profile routes through the switch flow back to Built-in (its dialog, below, applies). Empty state: `"No saved servers."`
    - **Switch flow** (tap non-active profile → M3 AlertDialog, destructive): title `"Switch server?"`, body `"This wipes ALL local data on this device — including any unsynced changes — and loads everything from \"<nickname>\" instead. The app will close; reopen it to continue."` On confirm, in order: (1) close the `ServerSessionGate` (every network-to-Room writer checks it before any write — sync apply paths, trends/analysis cache writes); (2) stop both sync schedulers, then **drain both sync mutexes by locking them** (an in-flight cycle runs to completion by design — the drain waits it out; its writes were already fenced by the gate); (3) `AnalysisStore.stopAndJoin()`; (4) cancel WorkManager work and await the `Operation` (guarded — `getInstance()` throws if never initialized); (5) one Room transaction: DELETE FROM `journal_trackers`, `journal_entries`, `journal_meta`, `coach_plans`, `coach_logs`, `coach_meta`, `payload_cache`, `trends_meta`; atomic active-flag `CASE` update; synchronous debug-log boundary line `server switch: <old> → <new>`; (6) delete `cache/shared/*` export/dump files; (7) `finishAffinity()` + `Runtime.getRuntime().exit(0)` — **the user reopens the app** (a task-flag "restart" guarantees no new process; close-and-reopen is deterministic). On next boot `ServerConfig` resolves the active profile once (suspend DAO under a bounded `runBlocking(Dispatchers.IO)`): exactly one active row → its URL; **no active row → Built-in**; **read failure or >1 active → fail CLOSED into a recovery screen** (retry action; no HTTP client, no schedulers — BuildConfig fallback with another server's residue in Room would cross-contaminate). Full sync happens organically (empty watermarks ARE the full-pull request); client ids regenerate lazily (verified: fresh process + no meta row → new UUID); trends/analysis caches refill on visit. No pre-switch sync attempt (the old server being unreachable is a primary switch reason — the dialog warns instead).
    - **Active-profile deletion** is NOT generic delete + switch: one transaction (wipe + delete row + clear flags) behind one dialog: `"Delete \"<nickname>\"? This also wipes all local data loaded from it and returns to the built-in server. The app will close; reopen it to continue."`
    - **Rejected alternatives** (recorded): live in-process switching (resetting every store's in-memory state + a mutable ServerConfig); a separate-process relaunch trampoline (ProcessPhoenix pattern — real complexity, OEM variance, for an action taken a few times a year).
13. **WorkManager flush (plan §3 debt, never built)**: one-shot `SyncFlushWorker` enqueued when the app backgrounds with dirty rows (`NetworkType.CONNECTED`, exponential backoff, unique work per module or one combined worker — implementer's choice, declared), executing the normal `triggerSync()` path (mutex-safe by construction: `tryLock()` skips if a foreground sync races it). The **6 h periodic refresh is deferred** (plan already marked it "revisit; battery vs warm cache") — plan.md amended. WorkManager dependency enters `:core:data` (androidx.work, catalog-pinned).
